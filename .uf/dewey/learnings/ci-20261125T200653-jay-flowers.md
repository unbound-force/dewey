A MegaLinter version bump (e.g. v9.3.0 → v10.2.0 in .github/workflows/mega-linter.yml) is only partially proven by its PR check: on pull_request events VALIDATE_ALL_CODEBASE is false, so only changed files are linted, whereas the first push to main after merge sets it true and lints the full codebase under the new bundled linter versions. The failure mode is fail-safe — a red MegaLinter on main blocks the release preflight, which requires MegaLinter success, so no bad artifacts ship — but the bump is not fully verified until that first post-merge main run passes. When reviewing the bump, confirm the new pinned SHA matches the upstream release commit named in the version comment (Dependabot derives it via the GitHub API, satisfying SHA verification), confirm .mega-linter.yml's whitelisted linter keys are all still supported by the new major, and watch the first main push for pre-existing findings surfaced by the new linter set. Dependabot's github-actions grouping uses update-types [minor, patch], so a major bump correctly arrives as an individual PR for manual review rather than a grouped batch.
